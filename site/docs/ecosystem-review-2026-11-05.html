The RWKV ecosystem for agentic RL — a verified review (2026-11-05)

Public, neutral version of the internal 2026-11-05 handoff. Every claim below is traceable to reports/skyrl/, reports/state/, reports/eco/ and their evidence/ directories. Confidence marks: ✅ verified by source · ⚠️ partially verified / needs qualification · ❌ refuted or corrected.

Abstract

RWKV's single-turn RLVR is mature and officially organized. Multi-turn agentic RL training is still a public gap: no public recipe, no public training result, no state-native rollout layer. But the ecosystem is fuller than earlier audits suggested: the rwkv-rs organization alone publishes 40 repositories, including an earlier native verl integration; community projects already publish a 568-question multi-turn agent exam with scores, and an 830-question BrowseComp-Plus evaluation package exists. Official G1l (2026-10-31) ships tool-call / multi-turn chat templates and points users to the community agent catalog. The accurate framing is therefore: the official organization does not train agentic RL, but has standardized the agentic interface and delegated practice to the community — while public multi-turn RL training remains absent.

1. Scope & method

  • Snapshot date: 2026-11-05. Sources: primary repositories, model cards, official docs; zero-API-quota method (git ls-remote, commit atom feeds, raw files, HTML).
  • Three parallel workstreams: (a) skyrl-rwkv deep-dive, (b) state layer (wkvm) + Megatron scale, (c) ecosystem inventory (rwkv-rs org) + official channels.
  • Confidence marks are used per claim; corrections to the prior audit are listed in §5.

Implication: the closer a component is to agents, the less likely it is to be commercially usable. This matters for any product plan built on top of the ecosystem.

3. What is verified

3.1 Single-turn RLVR (mature, official)

  • rwkv-rs/skyrl-rwkv — fork of NovaSky-AI/SkyRL, created 2026-08-30, active through 2026-10-31, Apache-2.0. Five launchers (antidoom/FTPO, flashreinforce, opd, sao, sft), algorithms GRPO/DAPO/CISPO/SAO/OPD/Anti-Doom/FTPO. Evaluation is math-only (eval/prepare.py: gsm8k / math_500 / aime24 / aime25 / aimo_progress_prize_1). ✅
  • Official 2026-10-26 seminar numbers: GSM8K avg@4 59.42%→71.85% (+12.43 pp) with 155-step warm-up + 1000-step DAPO; MATH500 avg@8 39.88%→49.75%; anti-doom repetition 63→0; async OPD +29.4% throughput. ✅
  • vLLM fork pin: rwkv-rs/vllm-rwkv@2852a7b1d (pyproject.toml:584), public repository, 2 commits behind HEAD 7a6adcc6. The previously assumed 67f0c599 is an old commit (2026-08-04) not in the branch history. ✅
  • CI: the fork inherits 16 workflows, all gated on github.repository == 'NovaSky-AI/SkyRL'; so the fork has no CI at all (the 3,354 lines of RWKV tests are real but never executed in CI). ✅

3.2 Earlier RWKV RL integration: verl-rwkv

  • Fork of verl-project/verl, branch rwkv, created 2026-05-21 (101 days before skyrl-rwkv), last commit 2026-08-02, Apache-2.0. Native rwkv_lm engine (EngineRegistry), RWKV7 GRPO launcher, MaxRL entry point, daily upstream rebase workflow; 43 RWKV files, 18 PRs. ✅
  • Same main contributor as skyrl-rwkv (Cai-z-us) → the history reads as "verl-rwkv stopped, work moved to skyrl-rwkv". skyrl-rwkv is the current base, not the only one. ✅

3.3 Multi-turn tooling: code exists, training does not

  • skyrl-rwkv has use_conversation_multi_turn, per-turn loss_mask (observation excluded), and RWKVTrajectoryLogger; but max_turns is never set in RWKV recipes (default 1), and skyrl-agent/ has zero RWKV references. ✅
  • The feat/heli-r00-training-eval branch (8 commits, 2026-10-24→28, +516/−48) adds bounded training/evaluation phases and a scoreboard callback python -m helicopter checkpoint-result <spec> train in its README. The rwkv-rs/Helicopter repository itself is publicly 404 (GitHub, Codeberg, HF all checked). ✅
  • skyrl-rwkv evaluation is math-only — no agent tasks. ✅

3.4 State layer: primitives exist, integration does not

  • xiaol/wkvm (Apache-2.0 declared in pyproject.toml, no LICENSE file): per-request state slots with create/snapshot/fork/hibernate/resume; RWKV-7 state enumerated per layer (recurrent_state fp32, conv_state, ffn_state). Documented RWKV-7 numbers: 8,077 tok/s @B256 (1.5B), 2,000 hibernated sessions @2.29 MiB, p50 8.2 ms warm resume (⚠️ p99 explicitly excluded by the authors; single-run measurements; no independent reproduction).
  • live-migrate is not implemented (wkvm/server.py exposes only /v1/states + /v1/generate; ROADMAP lists migration as deferred). ✅
  • Chat API hard-rejects tools / logprobs / custom stop (wkvm/gemma_server.py), which blocks RL rollout use without a state-service integration. ✅
  • Main branch froze after the technical-report publication (2026-08-02); the m4-qwen35-hybrid branch stayed active until 2026-09-10 (+12k lines, Qwen3.5 hybrid guest allocator). ✅

3.5 Scale: RWKV-Megatron

  • Real Megatron-Core integration (ModuleSpec injection, TP/PP/SP/CP), Apache-2.0, default branch muon (last commit 2026-07-06); branches 2026-10-10 (10-15), codex/rwkv7-cp (10-22), codex/qwen-rwkv28b-distill (10-30). ✅
  • 28B evidence exists but is short-run capacity only: on codex/rwkv7-cp, 4 layouts × 30 steps with machine- readable JSON (TP4/PP2/CP1: 75,829 MiB, 2.0712 s/step, final val CE 7.497223, no NaN/skip/OOM); the distill branch has 3 × 28B configs plus a capacity probe that explicitly "does not save checkpoints or certify model quality"; docs/, training-smoke/ are gitignored (0 files); the only 12-hour run in the org is 2.7B, not 28B. ✅ → Scale path = exists + engineering partially proven; training effectiveness unproven.

3.6 Evaluation layer

  • lm-evaluation-harness-rwkv / lighteval-rwkv / evalscope-rwkv forks form a production evaluation pipeline (scoreboard publishing branches, resumable orchestration, HTTP backends). benchmarks.toml lists 16 benchmarks, with the agentic category empty. ✅
  • rwkv-rs/browsecomp-plus-eval — reproducible 830-question BrowseComp-Plus package (search top-5 / get_document / final_answer, 100 steps, 3-way candidate router, vendored vLLM-RWKV, official judge). No scores, no root LICENSE. ✅
  • No-22-Github/RWKV-Agent (outside the org) — public 568-question multi-turn agent exam (15 scenarios, per-question verify.py) with public baseline numbers: G1l base 187/568 = 32.9%, NoRA adapter 320.5/568 = 56.4% (⚠️ the NoRA number comes from a different/earlier base model — not a strict same-base comparison). Assets are unlicensed. ✅
  • rwkv-rs/rwkv-skills mentions a public scoreboard in the "Helicopter repository" (which does not exist publicly); dashboard code exists in-repo but no public score data. ✅

3.7 Official positioning

  • G1l (rwkv7-g1l-13.3b-20261031) chat template supports multi-turn and strict model-generated tool-call prompts; the official prompt-format documentation has a function call section; the official hub card and RWKV-LM README point to the community agent catalog as "latest best practices for agentic work". ✅
  • At the same time, the official 2026-10-26 seminar describes a single-turn RLVR roadmap (math/reasoning/code), and the rwkv_lightning tutorial notes that real agent RL requires running tools yourself. ✅
  • Correct framing: official does not train agentic RL; it standardizes the interface and points to the community.

4. What is still missing (the actual gap)

  1. Public multi-turn agentic RL training recipe/results — current agent models are SFT/NoRA/MiSS adapters, not RL.
  2. Public scores on standard agent benchmarks — BrowseComp-Plus 830 / τ-bench / BFCL have no RWKV numbers; the agentic category in the evaluation pipeline is empty.
  3. State-native rollout layer — connect wkvm state slots → episode → per-token log-probs → reward, or use skyrl-rwkv re-prefill as the pragmatic first step.

6. Implications

  • If the goal is a stronger RWKV on verifiable tasks: use skyrl-rwkv + DAPO, copy the official 155+1000 recipe. No need to touch the agent layer.
  • If the goal is agentic RL: the parts exist but the assembly does not. Start by reusing the public evaluation assets (P0), then take the official single-turn RL path (P1–P2), then build the multi-turn rollout (P3: re-prefill first, state slots later). See ROADMAP.md.
